## Goal

A customer signed in with an email code joins a shop as a member, their earlier guest orders come along only when
they can prove those orders are theirs, completed paid orders earn stamps, and the reward is applied at checkout by
the database. This is the selling point (decision D4), so every stamp movement is in an append-only ledger.

## The linking rule (security; decided with the founder)

Paper 6.7 says past orders "with the same mobile number are linked". A mobile number is not verified in the MVP
(no SMS), so linking by the number alone would let anyone type a stranger's number and take their order history,
address and stamps. The rule instead:
- A guest `customers` row (same shop, same phone, `user_id` null) is linked to the login only when the caller
  proves it: `p_order_token` is the token of an order in this shop placed with that phone (the storefront passes any
  token it holds for the shop, so joining from the receipt or from a phone that ordered before just works), or the
  guest row's email equals the login's verified email.
- Without proof, and a guest row with that phone exists → `phone_needs_order` ("Join from your receipt page, or
  use the phone you ordered with").
- No row with that phone → a new member row.
- A row already linked to another login → `phone_in_use`.

### 1. Migration `<timestamp>_members_and_stamps.sql`

- `loyalty_rules` (pk `tenant_id`; paper 7.3; `stamps_needed` 1 to 50, `reward_amount` ≥ 0, `min_order_total`
  ≥ 0), created inactive for every existing shop in this migration, and by `create_my_shop` from now on (replace
  it, same signature). Owners `select` and `update` (active shop).
- `loyalty_ledger` (paper 7.3, append-only, `delta <> 0`, reason check from `enums.ts`; unique
  `(order_id, reason)` where `order_id` is not null, so an order earns or redeems once). Owners `select`; members
  `select` their own rows; no client writes.
- `customer_addresses` (paper 7.3, at most 5 per customer, one default). Members `select`, `insert`, `update`,
  `delete` their own rows through the policy `customer_id in (select id from customers where user_id = (select
  auth.uid()))`; owners `select`.
- `customers`: members `select` their own row (`user_id = (select auth.uid())`).
- View `customer_stamp_balances` (`security_invoker = true`): `customer_id`, `tenant_id`, `stamps` (sum of delta).
- `private.member_customer_id(p_tenant uuid) returns uuid`: the caller's member row in that shop, or null.
- `join_as_member(p_slug, p_name, p_phone, p_order_token)` (add `orderToken: z.string().min(8).nullable()` to the
  contract): signed in (`not_signed_in`); already a member here → return the account (`already_member` is not an
  error); applies the linking rule above; sets `user_id`, `member_since`, the login's email, and the name given.
  Returns `MemberAccount`.
- `get_my_account(p_slug) returns jsonb`: `MemberAccount` or `null` when signed in but not a member here (make the
  contract output nullable). Orders: the latest 20 for this customer.
- Earning: in `advance_order` on `completed` (replace the function, same signature): when the shop's rule is
  active and `subtotal - discount_total >= min_order_total`, ledger `+1 earned` for the order's customer. Guests earn
  too; the stamps show once they join and their row is linked. Paper 6.7: "a stamp is added only when the order is
  completed and paid" (completion already requires paid).
- Redeeming: replace `private.build_order` (same signature) so `useReward = true` needs a signed-in member of this
  shop with an active rule and a balance ≥ `stamps_needed` (`reward_unavailable`); `discount_total =
  least(reward_amount, subtotal)`; when placing, ledger `-stamps_needed redeemed` for that order. A signed-in
  member's checkout uses their member row (name and phone on the order still come from the payload).
- Reversing: in `cancel_order` and `expire_unpaid_orders` (replace both, same signatures), an order that redeemed a
  reward gets `+stamps_needed reversed`. Completed orders cannot be cancelled, so earned stamps never need reversing.
- Replace `get_storefront`: `stampRule` (active rule or null) and the real `memberCount` (`member_since` not null).
- `save_stamp_rule` is a plain owner `update` on `loyalty_rules` (RLS), no function.

### 3. Tests

pgTAP `06_members_and_stamps.test.sql`:
1. Linking with a valid order token works; with someone else's token, a token from another shop, or no token
   (and no email match) it raises `phone_needs_order`; a phone linked to another login raises `phone_in_use`.
2. Email match links without a token.
3. Earning: completed order ≥ minimum earns 1; below minimum earns 0; inactive rule earns 0; the same order never
   earns twice.
4. Reward: not enough stamps → `reward_unavailable`; enough → discount applied in both quote and place, ledger
   `-N`; the discount never exceeds the subtotal; a cancelled or expired order gives the stamps back once.
5. A guest's stamps appear in `get_my_account` after linking.
6. Member A cannot read member B's customer row, ledger or addresses; owners read their own shop's members only;
   `anon` reads nothing.
7. `get_storefront` shows the member count only when `show_member_count` is on.

Vitest: `stampProgress(balance, rule)` in core (stamps toward the next reward, `rewardReady`), contract parsing.
